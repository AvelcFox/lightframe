# Colored Lights — архитектура и анализ интеграции (Minecraft Fabric 1.20.1)

Документ фиксирует результаты анализа ванильного движка освещения и рендер-пайплайна
Minecraft 1.20.1, выбранные точки интеграции, модель смешивания света и компромиссы.
Имена классов/методов приведены по yarn mappings `1.20.1+build.10` и проверены по
реальным маппингам (см. `scripts/mappings_dump.txt`).

---

## 1. Цели и ограничения

* Настоящее RGB-освещение поверх **чистого ванильного рендера** — без Iris, OptiFine и shaderpack'ов.
* Свет должен **красить поверхность**, а не накладывать цветной фильтр на экран.
* Интенсивность падает с расстоянием, источники ограничены радиусом, несколько источников смешиваются.
* Не ломать: ванильный block light, sky light, chunk rebuild, блочный/сущностный рендер, ambient lighting.
* Минимум mixin'ов, каждый — с обоснованием; никакого пересчёта света на CPU на каждый кадр на каждый пиксель.

## 2. Как устроен vanilla light engine 1.20.1

### 2.1 Хранилище и каналы

* Два канала: **block light** (`LightType.BLOCK`, уровень 0–15) и **sky light** (`LightType.SKY`, 0–15).
* Значение канала — **напбл (0–15)** на блок. Данные лежат в `DataLayer` (2048 байт = 4096 вокселей × 4 бита)
  на каждый `LevelChunkSection` (16³), внутри `ChunkLightSection`/`ChunkSection`.
* Движок: `LevelLightEngine` (yarn: `LightingProvider` + `ChunkLightProvider` + `LightStorage`).
  Пропагация — BFS от источников с шагом −1 (непрозрачные блоки глушат сильнее); обновления
  инкрементальные, через очередь задач.
* Ключевой факт (проверено по маппингам): в 1.20.1 метод
  `BlockRenderView#getLightLevel(LightType, BlockPos)` (`net.minecraft.world.BlockRenderView`,
  intermediary `method_8314`) — **default-метод интерфейса**, единственная декларация во всей
  иерархии: ни `World`, ни `WorldChunk` его не переопределяют. Значит, «перехват света через
  World/LevelChunk», как в старых версиях, здесь не работает — запросы света уходят внутрь
  `LightingProvider`/`ChunkLightProvider`/`LightStorage`.

### 2.2 Числа света

* Один канал = одно целое 0–15. Ванила **не хранит цвет**: все факелы дают одинаковую «тёплую»
  яркость, цвет появляется только в таблице `LightmapTextureManager` (см. §3.2), зависящей от
  пары (blockLight, skyLight).

Вывод: цвет источника в ванильный light engine **не положить без замены формата данных**.
Замена формата (RGB в `DataLayer`) означала бы переписывание `LightStorage`/`ChunkLightProvider`
и клиентских снепшотов — именно то «переписывание Minecraft», которого мы избегаем. Поэтому
цвет хранится и распространяется **отдельным движком мода**, а ванильный канал используется
только как канал **интенсивности** (§5).

## 3. Как устроен чанк-рендер 1.20.1

### 3.1 Пайплайн сборки меша

1. `WorldRenderer` держит `BuiltChunkStorage` из `SectionRenderDispatcher.RenderSection`;
   секционный меш пересобирается задачей `RebuildTask` (пул потоков `ChunkBuilder`).
2. `ChunkRendererRegionBuilder.build(world, from, to, offset)` создаёт снепшот области
   `ChunkRendererRegion implements BlockRenderView` поверх `RenderedChunk` (палитры секций и
   block entities; **света в снепшоте нет** — свет запрашивается через поле `world`).
3. Для каждого блока: `BlockRenderManager.renderBlock(state, pos, region, matrices, vertexConsumer, cull, random)`
   → `BlockModelRenderer.render(region, model, state, pos, matrices, consumer, cull, random, seed, overlay)`
   → `renderFlat`/`renderSmooth` (AO) → на каждый квад
   `BlockModelRenderer.renderQuad(...)` → **`VertexConsumer.quad(entry, quad, r, g, b, a, light, overlay)`**
   (два перегруженных варианта, в т.ч. с массивами яркости для smooth lighting).
4. Жидкости — отдельный путь: `FluidRenderer.render(...)`, вызываемый из `BlockRenderManager.renderFluid`.

Проверенная сигнатура (yarn 1.20.1):
`BlockModelRenderer.render(BlockRenderView, BakedModel, BlockState, BlockPos, MatrixStack, VertexConsumer, boolean, Random, long, int)`.
Т.е. **у BlockModelRenderer на входе есть и позиция блока, и VertexConsumer** — идеальная точка
заворота consumer'а в декоратор.

### 3.2 Формат вершины и lightmap

* Формат: `position, color(RGBA), texture, overlay, light(UV), normal`.
* Цвет пикселя в ванильном шейдере ≈ `textureColor × vertexColor × lightmapUV`.
* `vertexColor` — произведение биом-тинта (grass/leaves/water) и AO/затенения грани.
* `lightmapUV` — индекс в текстуру-таблицу 16×16 (`LightmapTextureManager`), пересчитываемую раз
  в кадр по паре (blockLight, skyLight): гамма/яркость, ночное затемнение, Незер-затемнение и т.п.

### 3.3 Следствия (ограничения ванильного рендера)

* **Lightmap — 2D LUT по (block, sky)**: в неё нельзя закодировать цвет произвольной точки мира;
  цвет одинаков для всех блоков с одинаковой парой уровней → идея «раскрасить lightmap» отброшена.
* **vertexColor — единственный per-vertex RGB-канал**, доходящий до экрана в ванильных шейдерах.
  Единственная операция ванилы над ним — умножение (modulate).
* Пересборка меша секции дорога (миллисекунды) → число пересборок надо минимизировать и
  распределять по кадрам.

## 4. Возможные подходы и почему выбран конкретный

| Подход | Вердикт | Почему |
|---|---|---|
| Экранный цветной оверлей | ✗ | Запрещено ТЗ: не освещает геометрию. |
| Раскраска lightmap-текстуры | ✗ | 2D LUT по (block, sky): цвет не зависит от позиции в мире. |
| Замена формата ванильного light engine на RGB | ✗ | Переписывание `LightStorage`/`ChunkLightProvider`/снепшотов; высокий конфликтный риск. |
| Additive-проход (второй цветной меш поверх террейна) | частично | Настоящий additive, но дублирует геометрию и требует свой рендер-слой; отложено как опция Stage 4. |
| **Гибрид: канал интенсивности в ванильном block light + канал оттенка в vertexColor** | ✓ | Выбрано. Минимальные точки интеграции, ванильные шейдеры, свет реально «красит» поверхность, sky light сохраняется. |

## 5. Выбранная модель: двухканальный гибрид

Итоговый цвет поверхности (как его считает ванильный шейдер):

```
pixel = textureColor × (biomeTint × AO × rgbTint(pos)) × lightmap(blockLight', skyLight)
где blockLight' = max(vanillaBlockLight, luma(ourRGB(pos)))
```

1. **Канал оттенка** — `rgbTint`: собственный RGB-движок мода считает по блокам накопленный цвет
   (§6); он умножается в vertexColor через декоратор `VertexConsumer` в точке сборки меша.
   Модель отражения — ламбертовская по форме: `reflected ≈ surface × light` (умножение):
   белая стена рядом с красным источником краснеет, зелёная трава под красным светом темнеет
   (физично для узкополосного света).
2. **Канал интенсивности** — `luma`: luminance накопленного RGB (максимальный канал) масштабируется
   в 0–15 и берётся `max()` с ванильным block light в точке запроса. В полной темноте красный
   источник даёт block light ≈ своей яркости → lightmap светится → цветной тинт виден. Без этого
   канала в тёмной комнате свет был бы невидим (`tint × чёрный lightmap = чёрный`).
3. Sky light и обычные факелы не трогаем: мы только берём `max` в точке запроса.

Почему это не «полупрозрачный фильтр»: цвет попадает в **умножение на цвет каждой вершины
геометрии** — каждая поверхность красится индивидуально, с интерполяцией между гранями и
учётом AO. Это и есть освещение геометрии.

## 6. RGB-движок и модель смешивания

### 6.1 Представление

* Источник: позиция (double), RGB (float 0..1), intensity (float), radius (int), enabled.
* Эмиссия по каналам: `E_c = clamp(color_c × intensity, 0, 1) × 255` (int 0..255 на канал).
* Хранилище: разреженные `LightSection` (16³), `byte[4096 × 3]` (R,G,B на воксель, 12 КБ/секция),
  аллоцируются лениво — только там, где есть свет; удаляются при выгрузке чанка/обнулении.
  `maxLuma` секции кэшируется для быстрого ответа в горячем пути `getLightLevel`.

### 6.2 Распространение (LightPropagation)

* BFS по 6-связности от источника внутри бокса радиуса `radius` (радиус — полусторона куба влияния).
* Ослабление на шаг по каналу: `step_c = max(1, ceil(E_c / radius)) + opacity × ceil(E_c / radius)`,
  где `opacity = BlockState#getOpacity(world, pos)` (0 у воздуха, 15 у полного блока) — тот же
  источник непрозрачности, что у ванилы; полный блок гасит свет полностью.
* Слияние путей — **max по каналу** (как у ванильного block light): монотонность гарантирует
  завершение BFS и инкрементальные обновления. Источники смешиваются по каналам:
  R от красного + B от синего = (255, 0, 255) — фиолетово.
* **Обоснование модели смешивания (ТЗ §4):** выбрана **аддитивная per-channel модель** с max-слиянием
  путей распространения. Усреднение отвергнуто как физически неверное (два слабых источника
  давали бы тот же свет, что один); чистое суммирование при хранении отвергнуто (ломает монотонность
  BFS, даёт пересветы, требует per-source хранилищ ×N). Max-слияние консистентно с семантикой
  ванильного block light (уровень = максимум по источникам) и устойчиво к пересветам.
  Отражение от поверхности — умножение (§5), что в сумме даёт корректное аддитивное поведение:
  перекрытие красного и синего даёт фиолетовую засветку, белый добавляет все каналы.
* Сложность: изменение источника — `O((2r)³ × 6 × k)` посещений очереди, `k < 2` (улучшений на
  воксель). Для r=8 это ~10⁵ простых операций — миллисекунды; операция делится бюджетом времени
  на тики (§8).
* Удаление/перемещение: очищается бокс старого объёма влияния, затем повторная пропагация всех
  источников, пересекающихся с боксом (инкрементальная схема; пере-расчёт ограничен суммой
  объёмов, а не объёмом мира).

### 6.3 Dirty regions и перестроение меша

```
изменение источника
  → LightUpdateQueue (бюджет на тик)
  → BFS пишет в ChunkLightStorage, собирает затронутые секции
  → EngineListener.sectionsChanged(dirtySections)
  → клиентский бэкенд: scheduleSectionRender() только для этих секций
    (троттлинг: ≤ N секций за тик, остальное — в следующих кадрах)
```

Полного rebuild всех чанков не происходит никогда; перестраиваются только секции, где реально
изменились байты RGB. Движущийся источник распределяет dirty-секции по разнице старого/нового
боксов.

## 7. Точки интеграции (mixin'ы) — каждая с обоснованием

| # | Класс (yarn 1.20.1) | Метод | Зачем | Что меняет | Конфликты |
|---|---|---|---|---|---|
| 1 | `client.render.block.BlockModelRenderer` | `render(...)` | Единственная точка с `BlockPos` + `VertexConsumer` перед записью всех квадов блока | Заворачивает `VertexConsumer` в `TintingVertexConsumer`, умножающий RGB квадов на локальный цвет | Моды, тоже заворачивающие consumer (порядок mixin'ов); мы — прозрачный декоратор |
| 2 | `client.render.block.FluidRenderer` | `render(...)` | Жидкости не проходят через BlockModelRenderer | Тот же декоратор для воды/лавы | Аналогично #1 |
| 3 | `world.chunk.light.ChunkLightProvider` | `getLightLevel(BlockPos)` | ЕДИНАЯ точка всех световых запросов в 1.20.1 (проверено байткодом): `BlockRenderView.getLightLevel` — default-метод → `LightingProvider.get(type).getLightLevel(pos)` → `ChunkLightProvider`; покрывает сборку меша, сущности, BE и геймплей | `max(vanilla, lumaRGB(pos))` только для block-слоя (фильтр `lightStorage instanceof BlockLightStorage`); sky light не тронут | Моды, заменяющие весь light engine (редко); ранний выход по глобальному гейту |
| 4 | `client.render.entity.EntityRenderDispatcher` | `render(...)` | Тинт сущностей (Stage 3, экспериментально, за конфигом) | Декоратор `VertexConsumerProvider` | Моды, заворачивающие VCP; Fabric-рендер-события совместимы |
| 5 | `client.render.block.entity.BlockEntityRenderDispatcher` | `render(...)` | Тинт block entities (сундуки и т.п.) | Декоратор `VertexConsumerProvider` | Аналогично #4 |

Никаких инвазивных патчей `LightStorage`/`ChunkBuilder`/шейдеров. Все хуки выключаются конфигом
(`enabled=false` → декораторы возвращают исходный consumer, световой хук — мгновенный early-return).

## 8. Производительность

* **Никакого per-пиксельного CPU-расчёта.** CPU-работа: (а) BFS при изменении источников —
  событийно, с бюджетом времени (`updateBudgetMs` на тик); (б) семплинг RGB при пересборке меша —
  O(1) (Long2ObjectOpenHashMap + кэш последней секции) и только когда секция всё равно
  пересобирается ванилой; (в) luma-запросы — O(1) с быстрым выходом при пустом хранилище.
* **Кэши**: разреженные секции, кэш последней секции в семплере, инкрементальный BFS, dirty-набор.
* **Ограничители**: `maxLightSources`, `maxLightRadius`, `updateBudgetMs`, `maxSectionsRebuiltPerTick`
  (клиент), `lightingQuality` (LOW/HIGH: семпл по блоку vs по вершине).
* Память: 12 КБ на активную секцию (обычно десятки-сотни → единицы МБ), 0 без источников.
* Нет O(n²) по источникам: индекс источник→боксы, слияние по каналам в одном BFS-хранилище.

## 9. Iris / shaderpack

* Мод **не зависит** от Iris: детекция через рефлексию `net.irisshaders.iris.api.v0.IrisApi#isShaderPackInUse`
  без compile-зависимости.
* Бэкенды: интерфейс `ColorLightBackend` → `VanillaLightingBackend` (всегда) и `IrisLightingBackend`
  (при наличии Iris).
* При активном shaderpack тинт vertexColor по умолчанию **отключается** (пайплайн шейдеров может
  не уважать vertexColor или делать собственный цветной свет) — fallback исключает двойной тинт.
  Канал интенсивности сохраняется: пакеты обычно уважают light-координаты, динамический свет
  остаётся видимым (монохромно).
* Полноценный цветной свет под Iris требует поддержки самого пакета (чтение наших данных шейдером);
  API бэкенда оставляет точку расширения; патчить конкретные пакеты запрещено ТЗ.
* Fallback не крашит игру, пишет одно сообщение в debug log (`logIrisFallback`).

## 10. Сетевая модель и стороны

* Движок работает **на обеих сторонах** (ServerWorld — авторитетный, ClientWorld — для рендера).
* Синхронизация сервер → клиент одним payload'ом (`coloredlights:sync`, Fabric Networking v1):
  add/update/remove + bulk на входе в мир и смене измерения.
* Клиентские источники (API на клиенте) — чисто визуальные, на сервер не уходят.
* `affectGameplayLighting` (конфиг): luma учитывается в игровых запросах света (мобы не спавнятся
  в ярком цветном свете); отключается без потери рендера.

## 12. Известные ограничения (честно)

1. **Sodium** заменяет сборщик меша и не вызывает `BlockModelRenderer` → тинт под Sodium не работает
   (luma-канал работает). Нужен отдельный бэкенд (Stage 4+).
2. **Lightmap остаётся ванильным**: тёплый оттенок факела и Незер-затемнение накладываются на
   RGB-свет; в темноте яркость обеспечивает luma-канал.
3. Тинт — **умножение**, не сложение: поверхность не становится ярче, чем позволяет lightmap
   (в темноте яркость даёт luma-канал).
4. Iris-пакеты не получат цвет без их собственной поддержки (документированный fallback).
